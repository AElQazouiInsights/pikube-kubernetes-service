### 3.2 Bind9 TSIG key and equality check

- On `blueberry-master` (10.0.0.10):
  - Confirmed `/etc/bind/externaldns.key` exists and is included from `named.conf`.
  - Verified `named-checkconf` returns OK.
- Secret matching (done without printing raw secret):
  - Computed SHA‑256 hash of Vault TSIG:
    - `vault kv get secret/ddns-bind9` → `.data.data.key` → `sha256sum`.
  - Computed SHA‑256 of Bind9 TSIG:

  - Both hashes identical:
    - `f3f108ffbde48f4c16105ace08f25cd07c0f9394472d391610e562e670242187`.
  - Conclusion: **Vault TSIG = Bind9 TSIG**, so Vault is the canonical store for the existing TSIG key.

### 3.3 dnsmasq / split‑horizon sanity check

    - `local=/picluster.quantfinancehub.com/`, `domain=picluster.quantfinancehub.com`.
    - Multiple `host-record=...` for nodes and service VIPs (`argocd`, `monitoring`, `longhorn`, etc.) pointing at `10.0.0.100/101`.

## 5) Debug Pod Pattern (docs/4-kubernetes/2-debug-pod.md)

### 5.1 Doc intent and content

- The doc describes a **“PiKube Debug Pod”** as a Swiss‑army‑knife container:
  - Base image: `ubuntu:24.04`.
  - Tools: `curl`, `wget`, `ping`, `netcat`, `nmap`, `dnsutils`, `tcpdump`, `vim`, `htop`, `strace`, `git`, `python3`, plus common Python packages.
  - Entrypoint: `sleep infinity` to keep the pod alive for `kubectl exec`.
- It also suggests:
  - Multi‑arch build with `docker buildx` and push to a registry.
  - Quick alternatives using public multi‑arch images:
    - `nicolaka/netshoot:latest`.
    - `wbitt/network-multitool:latest`.
  - Patterns:
    - Static pod in `debug` namespace.
    - Ephemeral `kubectl run ... --rm`.
    - Ephemeral `kubectl debug` containers attached to existing Pods.

### 5.2 Live validation and best‑practice decision

- For validation, created a **temporary** debug pod using netshoot instead of custom image:
  - Manifest (not committed): namespace `debug`, pod `pikube-debug` with:
    - `image: nicolaka/netshoot:latest`.
    - `command: ["sleep", "infinity"]`.
  - Commands:
    - `kubectl apply -f pikube-debug.yaml`.
    - `kubectl -n debug get pods` → `pikube-debug` in `Running` state on `lemon-worker`.
    - `kubectl -n debug exec pikube-debug -- bash -lc 'which dig curl ping'`:
      - Confirmed `/usr/bin/dig`, `/usr/bin/curl`, `/bin/ping` present.
- Clean‑up:
  - `kubectl delete -f pikube-debug.yaml` → namespace `debug` and pod removed.
- Best practice conclusion:
  - We *do not* keep a long‑lived “god pod” in the cluster.
  - The PiKube pattern is:
    - Have a **standard toolbox image** (either custom or public).
    - Use it **on‑demand** via:
      - `kubectl run ... --rm`.
      - `kubectl debug` ephemeral containers.
    - Only create a static debug pod temporarily during investigations, then delete it.
  - The doc reflects this by showing both the static pattern and the ephemeral `kubectl run` / `kubectl debug` usage.
